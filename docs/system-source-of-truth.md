# System Source Of Truth

> Status: active
> Last verified: 2026-08-27
> Scope: authoritative sources for runtime state, configuration, governance, data, and frontend contracts.

本文回答一个问题：当文档、注释、接口、数据库和历史理解冲突时，到底以哪里为准。

## 1. 总规则

1. 运行态事实优先于历史注释。
2. 数据库事实优先于临时日志片段。
3. 当前服务入口优先于旧脚本。
4. `RiskPolicyService` 和 `DecisionPolicy` 的权力边界优先于旧自动化路径。
5. 文档只描述事实，不替代运行态审计。
6. 一个事实只能有一个生产计算者和一个写入者；其他模块只能消费或投影。
7. canonical authority 建立后，旧计算、旧写入口、旧字段回退和实现耦合测试必须在同一阶段删除。
8. `unknown`、`warming_up`、`stale`、`error` 保持原语义，任何层都不得通过默认值把它们转换为 known/safe。

### 1.1 三层生产权力

生产开仓链只保留三层权力：

| 层 | 负责 | 不负责 |
|---|---|---|
| Safety | broker/account/positions/spot、unknown execution、本地 latch、emergency 等必须立即禁止新增风险的硬事实 | 不计算 alpha、VaR/CVaR 或最终仓位 |
| Readiness | 只读检查 canonical 事实是否存在、新鲜、可用，并投影 blocker | 不重新计算风险、不写控制状态、不清理 latch |
| Risk sizing | 基于冻结输入计算 exposure、VaR/CVaR、stress、concentration 和最终 candidate volume | 不拥有发布开关、进程健康或前端展示判断 |

同一 blocker 只能由其权威 owner 计算一次，并发布稳定 reason code。API、readiness、
release preflight 和前端只能复用该结果，不得通过再次读取原始输入形成第二个裁决。
新增聚合对象只有在能够立即替换并删除多个现有终局判断时才允许；不得为了“统一”
再建立第四套门控或写入口。

### 1.2 仓位监督与系统记忆边界

- `PositionSupervisor` 的普通 `tighten/reduce/close` 继续采用唯一链路：
  `supervisor verdict -> RiskPolicy -> broker -> lifecycle -> fresh reconcile -> trace`。
  `governed_execute` 是当前 active live 语义；历史 observation 和 learning-shadow 不得回到 broker。
- 新仓位在成交前由 live backend 选择一次监督模板，并把规范化完整快照、版本、hash 和来源保存到
  `entry_protection_plan.supervisor_binding`，随 `recovery_position_state.recovery_meta_json` 恢复。
  已绑定仓位的普通软策略只读自己的快照；全局 `RuntimeConfig.position_supervisor_template_id` 只做
  新仓位默认基线和旧仓位 `legacy_global_fallback`。缺失、篡改或来源不明时保持
  `unknown/hold`，不伪造历史绑定；硬安全收紧仍由当前 Safety/RiskPolicy 独立执行。
- `runtime_kv[position_supervisor_selection.v1]` 是唯一记忆到 live 的选择投影，由既有 learning worker
  的 `position_supervisor_governance` 阶段生成，live backend 只在成交前或稳定已收盘 bar 边界读取；普通
  tick 不重新查询记忆。已有仓位切换受 Demo、known facts、无未决执行/对账、连续稳定 bar、冷却期和
  单仓次数限制，且只更新该仓位 binding，不修改全局模板。
- 仓位治理的“系统记忆”按层区分：canonical trace/counterfactual 是事实，监督训练样本是资格化学习记录，
  `experience_memory` 是可重建的交易 lesson，`brain_memory`/`posterior_arbitration` 是有界检索和后验索引。
  后两者只提供 memory/critic/context，不能直接授权 live 动作；真正改变模板必须经过 policy suggestion、
  V16、RiskPolicy、Coordinator、application/effect 和可回滚配置投影。
- 事实缺失、来源不明或记忆完整性异常时保持 `unknown/warming_up/stale/error`，不得用默认值补齐，
  也不得把单条记忆或单次反事实直接升级为全局策略结论。

### 2.1 Live broker snapshot 与循环心跳

| 事实 | 唯一生产者/写入者 | 约束 |
|---|---|---|
| account/positions fresh reconcile | `live_loop_tick_runtime` 串行 owner + `CTraderBridge.reconcile_positions/reconcile_account` | 每个 tick 先取得一份 `PositionReconcileResult`，账户对账复用其中已确认的 PnL；不得为同一 tick 再次查询相同 PnL |
| live loop completed observation | `live_loop_runner` + `live_service._set_loop_diagnostic` | `_diag.ts` 只代表完整 tick 完成时间；phase/start 时间不能冒充完成心跳 |
| Safety heartbeat | `LiveLoopController` / Safety plane | 只表示 Safety 阶段完成并继续独立 fail-closed；不替代 account/positions freshness，也不使公共 loop fact 忽略较旧的完整 tick。串行 Safety 阶段可额外发布仅供 watchdog 识别“正在执行而非卡死”的 progress 标记；progress 不能解除 20 秒完成心跳或最终开仓对账门 |

串行 broker RPC、风险保护和风险指标计算都计入 tick 周期。5 秒是目标周期，不是额外 sleep；若工作已经超过目标周期，下一轮立即开始，不再追加等待。20 秒 freshness 到期时必须显示 `stale` 并阻断新增风险，不能把阈值调大来掩盖后端停滞。

仓位监督选择的 `off` 只是无合格证据时的安全启动基线，不需要人工把它改成
`demo_execute`。learning worker 在投影达到资格后会自动通过既有 V16、RiskPolicy 和
Coordinator 进入有界 Demo；`live_execute` 仍不准入。这里保留的是执行安全边界，不是新增
人工审批闸门。

判断原则：

- 生产自治动作不应直接修改 `settings.yaml`。
- 看到内存配置异常时，先查 overlay、snapshot 和进程内 `runtime_config.shared()` 是否已刷新到最新 overlay hash。
- readiness 的 runtime drift 比较对象是有效权威配置（YAML base + persisted overlay）与进程内 singleton；YAML 与 overlay 的差异单独作为 `overlay_changed_keys` 信息展示，不得把合法自治 overlay 误报成 drift。
- 可疑测试 overlay 不应被生产启动恢复。
- 空 `mutation_id`、悬空 mutation、hash 不一致或缺少完整 legacy authority manifest 的 overlay 不能授权新增风险。启动/轮询必须持久化 `governance_authority` no-new-risk cause；已有仓位需要的 supervisor/收紧控制可作为隔离只读投影继续保护，但扩张或方向未知字段不得从悬空 mutation 恢复。operator review 只能通过 `RuntimeConfigOverlayService.review_legacy_quarantine()` 对精确 overlay hash 逐 key 回填，调用方不能自报 risk class；任何非收紧 key 必须改走 typed committed mutation，不能伪造 legacy 放行。
- 自治 writer 只能提交作用域内的局部 patch；禁止用读取时的陈旧全量权重覆盖其他治理动作。overlay row 与 `runtime_config_snapshot` 任一写入失败时，内存配置不得提前变化。
- incident control 模式变更必须先过 `RiskPolicyService.evaluate("set_incident_control")`，再提交 `IncidentControlPlan`。任何 action 名或 caller `risk_reduction` 都不能改变风险分类；生产收紧在 PG/Coordinator 前先持久化本地 fail-closed latch，overlay/审计失败只形成待恢复投影，不能改变已经生效的新增风险阻断。
- `runtime_incident_mode` API 的 `mode/effective_mode` 必须包含本地 latch 的收紧效果，并额外暴露 `configured_mode`。本地账本保留 v1 envelope 并以 additive `live_no_new_risk_latch_causes.v2` 事件重放多原因集合；历史 v1 activate/clear 可继续读取，新代码不再追加 blanket clear。若 PG 故障时 `incident_control` cause 已生效但 configured 仍是 `normal`，必须先把 `no_new_risk` 作为收紧 mutation 补交 committed 投影，再走相同 typed thaw；非有界 Demo 仍需 step-up + V16，有界 Demo 显式 operator 可确认后直接提交。若只剩独立 safety cause，configured 可以是 normal，但 effective 必须继续为 no_new_risk 且报告 `resume_required`。
- parameter template、position supervisor template 与 model influence stage 的可执行切换必须先由领域服务完成证据和 RiskPolicy 判断，再构造 typed plan。`dual_record|enforce` 下，Coordinator 的 transaction writer 将 template registry/application/effect/reservation、`policy_suggestion.applied_mutation_id` 与 overlay/snapshot/V16 finalize 绑定为同一 committed mutation；调用方不能通过 `risk_reduction` 自报免闸。`off` 只保留一版兼容写法。
- position supervisor 模板手工/自动 apply 与 effect rollback 共用 `PositionSupervisorGovernanceMutationService`；parameter effect rollback 不再先写 registry 再静默 sync runtime。model demote 只提交最小 stage patch，原因和时间进入 evidence，避免把纯风险收紧混成扩张 mutation。只写 snapshot、只改 registry/application 或只改内存均不算生效。
- position supervisor 的自动路径只接受 `candidate_id + source_agent=v16_brain + bridge.command_owner=v16_brain` 的 V16 bridge；先以该 `candidate_id` 领取命令，再把 command id/token 原样交给 `PositionSupervisorGovernanceMutationService` 的 Coordinator transaction。旧 advisory 可保留为审计观察，但必须 terminalize，且不得占用 V16 candidate review 的 conflict surface。
- position supervisor 的 active 模板边界固定为 `risk_boundary.adaptive_execution_mode=governed_execute`；`observation_only` 只作为历史 trace/learning-shadow 的审计值，禁止新 live trace 使用。Demo 普通 trend/range 的 `tighten/reduce/close` 统一从 supervisor verdict 进入 RiskPolicy、cTrader broker action、lifecycle event、fresh reconcile 和 `position_supervisor_trace`；风控拒绝、broker unknown/failed、保护校验和对账仍 fail-closed。`autonomy_demo_auto_apply` 只控制已通过证据/V16/Admission/RiskPolicy/Coordinator 的治理 mutation，不控制普通持仓监督执行。生成候选仍必须是单 control、单 regime stratum，并具备 base template、candidate patch、generation context、replay/counterfactual evidence；`largest_contribution_factor` 仍是 observational，不能单独授权因子或模板 mutation。
- position supervisor 失效证据的生产者（2026-08-26 补齐）：`entry_regime` 由开仓链 `_persist_pending_entry_protection_plan` 用决策时点 `_current_regime_hint()` 盖章写入 recovery meta；`signal_reversal` 由监督器上下文构建处比较最新 committed composite direction 与持仓方向产生；`thesis_broken_confirmations` 由 path-metrics 状态机逐观测递增、intact 归零。transition_confirming 姿态允许盈利单在 profit_protection_window_ready 且 giveback≥tighten 阈值时执行 tighten（summary_reason=`transition_profit_protection_tighten`），close/reduce 权力范围不变。
- `autonomy_mode=live_autonomous` 不是风控旁路；解锁必须写 `live_autonomy_unlock_event` 并提交 `AutonomyControlPlan`，由 committed overlay/snapshot 恢复。撤销先激活本地 latch，再提交治理投影；PG 或事件审计失败时返回 `local_safety_latched_projection_pending`，不能把 revoke 解释为失效并继续开仓。未解锁或预算触顶时，`RiskPolicyService` 阻断 open/update/promote 等新增风险动作，只允许 close/reduce/tighten/rollback 等降风险动作继续走受控入口；live 开仓路径若收到 `live_autonomy_budget_breach`，必须通过 `RuntimeIncidentControlService` 请求收紧到 `no_new_risk`，不能直接改 overlay。
- Coordinator 只管理治理事实和 RuntimeConfig 投影；broker close/reduce/tighten/emergency-close 与本地 fail-closed latch 绝不调用或等待 Coordinator、PostgreSQL、因子、学习或 mutation audit。治理写失败只能产生 pending projection/outbox，不能重写 broker action 结果。

判断原则：

- `bb_width/adx/atr_ratio/keltner_width` 是 context，不是方向投票。
- context 可以影响状态、阈值、仓位，但不能直接改变多空方向。
- live 信号决策层只产出 `CompositeSignal`、context policy effect、`GateResult` 和审计 payload；交易授权仍必须进入 `RiskPolicyService`，权重治理仍必须进入 `DecisionPolicy`。
- shadow 因子不直接交易，必须经治理晋升。
- 兼容 `/api/shadow/promote` 只提交 `PROMOTION_PREPARED`，不能直接调用 Registry promotion；ACTIVE 还必须同时具备规范化 DSL AST SHA-256 身份、64 位 artifact SHA-256、新鲜 loaded projection ack、显式 `enabled=true`、显式正权重和新鲜 `HEALTHY` 证据。任一证据缺失均 fail-closed。`/api/shadow/demote` 只提交 typed `QUARANTINED/RETIRED` mutation；Registry removal 发生在 commit 后投影阶段。
- 自动 discovered promotion 同样分成两个治理周期：先由 Factor Governance 提交 `PROMOTION_PREPARED`，live warmup/hot reload 确认实际可加载后，再由后续 V16 delegate 通过 `FactorLifecycleService.activate()` 提交 ACTIVE；候选识别只读取 canonical lifecycle 的 `origin + stage + durable identity`，不得依赖准备后会从 `shadow` 变为 `discovered` 的 catalog source。旧的直接 `RegistryAdapter.promote + runtime weight` 组合不再是激活入口。
- discovered/生成因子没有显式权重时权重为 0 且 `used_in_score=false`；不得再使用隐式 `0.3`。Live admission 必须同时满足 lifecycle committed fact 和 current projection，不能只看 RuntimeConfig/Registry。
- 上述内置结构候选的 `enabled=true` 只表示允许进入 shadow 计算，不表示参与方向评分；`lifecycle_status=SHADOW` 或权重为 0 时不参与开仓方向，自动启用必须满足健康分 ≥ 70、健康样本 ≥ 500、非衰减且模型弱势证据通过，并保留 runtime snapshot/rollback。
- Fibonacci 因子不得使用未确认的 swing high/low；摆动点等待右侧确认 K 线后才可作为锚点，回撤位置、水平接近度和反弹确认分别作为 context/context/alpha 候选。
- `FactorGovernanceOrchestrator` 是因子晋升、Canary 回滚、禁用和退役的唯一调度执行者；Evolution 只能写证据和候选。每个周期固定先执行 rollback/downweight/quarantine/retire，再检查 expansion posture；只有 preflight 已找到具体 builtin activation/restore、shadow promotion 或 redundancy mutation 时才领取 V16，没有扩张动作固定返回 `idle_no_expansion_action`，不得误报为 V16 blocker。preflight 必须复用实际执行门的 canonical lifecycle expression、fresh health、pending-effect 和 promotion evidence；不能把只能在 audit/canary 中找到、缺 canonical definition 或无法进入 typed lifecycle 的对象报成可行动候选。freeze、operator pause 或缺 V16 只能阻断真实恢复/晋升等扩张，不能推迟风险收紧。参数模板在该周期只产生 evidence handoff，其 mutation 和 V16 由 `autonomous_learning` 自己拥有。AWE 只在持有 live attribution pipeline 的 backend 进程运行。`autonomy_expansion_frozen` 仅对非 Demo/实盘权限面生效；`demo_nursery` / `demo_autonomous` 保持 AWE、Factor Governance 和 Canary 推进运行。独立的 `governance_expansion_paused` 是 operator-owned 全模式 kill switch，任何模式都没有 Demo 豁免，自治服务不能修改它；暂停期间 observation/research 和显式 rollback/retire/quarantine/downweight/tighten 继续，其他治理扩张 fail-closed。所有实际权重 patch 仍必须统一调用 `FactorWeightChangeService`，先过 `DecisionPolicy`、有界经验先验、共享 `LearningExperimentAdmissionService` 和 `RiskPolicyService`；风险扩张额外要求 V16，收紧由 Coordinator 根据 before/after 免 V16。`dual_record/enforce` 下 batch admission 在 Coordinator 的 scope/global lock 内重验，reservation、application、effect、overlay/snapshot 和 V16 finalize 要么全部提交、要么全部回滚，不在事务前留下 `prepared` 污染。因子扩张候选（builtin activation、active zero-weight restore、quarantined builtin restore、shadow promotion）在 preflight 阶段统一过 `posterior_expansion_verdict` 后验闸：复用 `learning_application_effect`（scope_type=factor、非 rolled_back/superseded 的最新有效 effect）作为唯一后验事实源，`delta_avg_reward < factor_governance_posterior_block_delta`（默认 -0.05）且 `observed_trade_count >= factor_governance_posterior_min_samples`（默认 10）时返回 `blocked_by_posterior` 剔除候选；样本不足时返回 `posterior_degraded` 保留候选但标记降级；无记录或 delta 非负返回 `posterior_ok`。该闸是扩张方向的"上次这么干亏了就不重复"防抖，与既有 `_rollback_failed_actions` 回滚路径共享同一后验表和过滤规则，不新增写入者；生产状态查询不确定时 fail-closed 阻断扩张，测试/研究库缺失账本视为无后验证据。preflight 结果新增 `posterior_blocked_ids`/`posterior_degraded_ids` 只读投影，V16 delegate 判断粒度不变（仍批轮次、specialist 选因子）。降权与恢复均按当前市场状态条件化（批次 C/D）：preflight 单点调用 `project_current_market_regime()` 解析当前 regime（复用 `_current_market_regime_projection()`，不各自重算），逐因子取 shadow 最新 `regime_fit_score`（`_shadow_regime_fit_score()` 共享提取）与 `factor_governance_regime_fit_ok_threshold`（默认 0.5）比较。降权侧（`_downweight_weak_alpha`）：模型判定全局弱但当前 regime 下 fit 达标 → 标记 `regime_mismatch` reason code、权重不动（\"只是当前市场不适合，不是永远不能用\"）；缺 regime 投影或 fit 证据时 fail-safe 落回既有全局弱路径，绝不侵蚀风控（`_regime_mismatch_verdict()`）。恢复侧（active 零权重恢复、quarantined builtin 恢复候选）：`_regime_suitable_for_restore()` 在既有后验闸之外叠加 regime 闸——后验闸管\"上次恢复亏了\"（blocked_by_posterior），regime 闸管\"当前市场适不适合\"（fit 不达标 → 不恢复，reason 带 regime 归因），二者正交；缺 regime 投影或 fit 证据时 fail-open 落回既有恢复路径，不饿死正常恢复。condition 判断不做第二个计算者：regime 投影、lightgbm 条件弱分数分别只在 `market_regime.py` 与治理模型单点生产，orchestrator 只消费。
- hourly Evolution 仅由 learning worker 在 minute `23,53` 运行；Backend 的 `EvolutionKernel` 重任务注册和启动 catch-up 已删除，不保留第二 owner。每次成功提交 `factor_health` 后，必须在同一 coordinator 所有权内按 `health -> V16 decision -> Factor Governance` handoff，并携带唯一 `factor_health_cycle_id`；健康未提交时不得触发恢复型治理。GP 搜索先比较 `evolution_cycle_watermark.v1`，同一闭合 bar、输入、配置和代码只运行一次；相同输入仍执行健康、Canary、退休和 effect 维护。候选积压达到 `QUANT_CANARY_EVALUATION_LIMIT` 时只排空存量，不注册新 GP。独立 Factor Governance 仍只在 minute `15,30,45` 运行；启动补偿、治理 preflight 与最终 lifecycle 门复用 900 秒健康时效。V16 对 concrete expansion preflight 只签发一次 `run_batch_fixed_manifest` 委托；Factor Governance 必须用相同 preflight fingerprint 和 candidate count 重验 batch manifest，不能把新候选追加到已签发命令。成功 mutation 必须 `finalized/apply_count=1`，无 committed action 必须 `cancelled/apply_count=0`。V16 失败时扩张 fail-closed，但 rollback/downweight/quarantine/retire 继续。hard-disable streak 只随新的 evidence cycle fingerprint 增加。
- 被治理隔离的 builtin alpha 因子通过 `FactorLifecycleService.quarantine()` 原子写入 `QUARANTINED`、`enabled=false`、显式零权重和 committed mutation；builtin callable 保留在代码 Registry，避免运行时代码删除。`QUARANTINED/RETIRED` 都是不可反向扩张的终态，dual-record/enforce 模式禁止 generic overlay 将其恢复为 ACTIVE；代码修订后必须使用新的版本化 builtin factor name/code-bound identity 从 SHADOW 重新验证，同名定义冲突 fail-closed。仅 coordinator-off 保留一版旧 restore compatibility，不能进入最终 enforce 路径。
- Canary 阶段推进不得重复消费相同历史聚合窗口；首次 SHADOW 可用已有 OOS bootstrap，后续阶段必须满足 `fresh_evidence_bars`，数据/结果指纹和 stage watermark 必须进入审计。
- 搜索/进化生成的 DSL 因子必须先通过 `parse_dsl()`；解析失败的表达式不能注册为 shadow 因子，历史残留坏 DSL 只能作为健康/治理噪音进入 `invalid_dsl` 审计，不能继续执行计算。
- 可执行治理证据统一调用 `governance_eligibility.v1`：必须 matured、full 或 verified recovered、无系统污染、model-ready、显式允许 executable governance 且 lineage 唯一完整；full 权重 1，verified recovered 上限 0.5，partial/missing/contaminated 权重 0。样本物化与 `repair_evidence_contracts()` 共用同一 normalization/evaluator，repair 不得从 `sample_type` 推断 executable 权限；污染、pending、缺 lineage 或未验证 recovered 不得进入强训练/强治理。
- canonical_v2 training_sample_row 的 eligibility version/fingerprint/weight 是 durable fact；entry cluster、event window、entry quality materializer 只消费当前 version 且 weight > 0 的样本。`PolicySuggester` 的 factor experience 路径也必须按同一 eligibility contract 写 `experience_pattern_stats` 的 raw/effective/weighted 指标，并把当前 version/fingerprint 原样绑定到 `policy_suggestion`；不完整、污染或 lineage 缺失的经验只增加 raw 观察，不得生成可执行建议。Governor 遇到 suggestion/stats fingerprint 缺失或不一致必须拒绝，不能回退使用 raw count。
- entry-quality 的 `weak_signal` 控制只允许当前治理版本、当前 eligibility fingerprint、成熟且无污染的独立 position 样本生成；旧的无资格、旧版本或 fingerprint 失效建议保留审计并转为 `invalidated_evidence`，不能占用当前 scope/action。建议 ID 必须包含 eligibility fingerprint。
- `activate_entry_quality_control` 是 `entry_quality` control surface 的 typed domain-only mutation：Coordinator 不伪造 RuntimeConfig 字段，在同一事务内提交 suggestion=`applied`、`learning_application_log/effect` 和 committed mutation。Demo 每周期最多应用一个 weak-signal 控制；激活属于风险收紧，删除、降低阈值或放宽仍按扩张经过 V16、DecisionPolicy 与 RiskPolicy。live loader 只读取 `applied + committed mutation`。
- 污染证据导致的 entry-quality 回滚必须复用同一 Coordinator：以原 mutation 的 `rollback_json` 和 predecessor lineage 为唯一目标，在一个事务内终止污染 suggestion/application/effect、恢复 predecessor suggestion 并绑定新的 committed risk-tightening mutation，随后将原 mutation 标为 `rolled_back`。禁止直接改 RuntimeConfig，也禁止只改状态后退回静态基础阈值。
- disabled/DEAD 因子应被 engine、compositor、AWE、readiness 一致排除。
- 因子组合体检只能产生 `issues` 和 `recommendations`；默认 `build()` / readiness 使用 Factor Catalog `used_in_score=true` 统计当前实际参与评分的 alpha，显式传入 runtime config 的测试/分析可保留配置全量口径；后续 pruning、降权、禁用或晋升仍必须走 `DecisionPolicy`、`RiskPolicyService`、runtime overlay/snapshot 和治理审计。
- 因子裁剪候选只能作为多智能体复盘、反证和治理提案草稿输入；任何实际权重变更仍必须先形成受控提案，再经过 `DecisionPolicy` 和 `RiskPolicyService`。没有近期 canonical factor_snapshots 参与记录、或近期平均贡献接近 0 的因子不能占用 demo governance 桥接名额；`dsl_auto` / `pca` 若不在 runtime config 但曾在真实决策快照中以非零权重/贡献参与，只能保留 snapshot-only research 观察，不能物化/晋级为可执行 downweight 候选。已经从当前 RuntimeConfig 权重事实源移除或权重为 0 的因子，其旧候选和旧建议必须 supersede，不能借历史权重重新启用。
- 因子裁剪反证必须在 pruning candidate 晋级前运行；强保留证据或 regime exception 会阻止 `governance_ready`，但不会直接恢复权重或提交反向提案。
- 因子裁剪治理候选可以写入 `brain_governance_candidate`，并可在风险预览、DecisionPolicy 预览、弱健康证据、反证检查和冲突检查通过后晋级 `governance_ready`；`demo_nursery` / `demo_autonomous` 下允许通过 `factor_pruning_governance.bridge_ready_candidates` 限速桥接到 `policy_suggestion`，但每个候选必须先由 `BrainGovernanceCandidateReviewService.review_candidate` 生成审查记录且 `bridge_ready=true`，再由 `RuleEvolutionGovernor`、`DecisionPolicy`、`RiskPolicyService`、runtime snapshot 和回滚证据约束实际应用。
- Candidate review 顶层 `bridge_reason` 必须与最终 `review_status` 对齐；原始 preview reason 只保留在 `bridge_preview`。`needs_evidence` 显示具体 gap，conflict/expired/submitted/bridge_pending/awaiting_execution 等状态显示最终状态；review 仍不等于 submit 或 applied。候选进入 `bridge_pending` 或 `awaiting_execution` 后，Fact 应报告 `pending_execution`，不能继续伪装成 stale review。
- 因子惩罚建议只消费 `primary_responsibility`、`worst_factor`、`factor_conflict`、`factor_contribution_review` 和 counter-evidence；责任域为 `exit`、`holding`、`data_quality` 或 `parameter` 时，raw `largest_contribution_factor` 不得生成因子惩罚或 lifecycle mutation。
- 因子治理效果回流只解释和复核已经应用的治理建议；效果比较优先使用精确 regime。精确前/后样本不足时，只有去污染后的前后样本都达到完整 observation window，才允许标记 `comparison_basis=unstratified_bounded` 并做有界归因；否则保持 observing 或转 inconclusive，不能触发强化/回滚。效果变差时由 `RuleEvolutionGovernor.reconcile_application_effects` 标记回滚/无效，下一次权重同步自然移除学习偏置，不能直接绕过 `DecisionPolicy` 写权重。

判断原则：

- 风控不产生 alpha，但拥有最高执行裁决权。
- 因子治理、模板切换、回滚都不能绕过 RiskPolicyService。
- live 日内熔断可以做执行快停，但阈值必须来自 `RiskLimitSnapshot`，不能在 live loop 内另设事实源。真实 cTrader Demo 且处于 `demo_autonomous`/`demo_nursery` 时，连续亏损和日内 drawdown 的 session circuit 只记录 observation，不执行快停；实盘及无法确认 Demo 的环境仍强制执行。
- `autonomy_mode=demo_autonomous` 和 `demo_nursery` 的真实 demo 采样都使用 `max(risk_max_daily_trades, demo_learning_max_daily_trades)` 作为明确日交易上限（当前二者均为 10），不再以 0 表示无限制。该阈值只通过 `RiskLimitSnapshot` 输入 `RiskPolicyService`；Demo 的最小量探索和 session circuit observation都不绕过断连、stale market、有效止损、实际止损风险、仓位、volume、日亏损 2%、最大回撤 8% 或其他运行健康裁决。
- 宽松 Demo 账户阈值（当前允许日亏损 50%、日交易 100 笔）必须同时满足有效下单和 cTrader host 为 `demo.*`；非 Demo host 启动时最多接受日亏损 5%、日交易 20 笔，否则 `execution_semantics` fail-closed，避免配置迁移把 Demo 风险预算带入真实账户。
- `autonomy_mode=demo_nursery` 是 demo 学习育苗模式，不是通用 live 风控旁路；`RiskPolicyService` 会把 `loss_cooldown_active`、`consecutive_losses`、VaR/CVaR、同向学习冷却、entry quality 和 event-window learning control 记录为 `demo_nursery_observations`，session circuit 同样只观察。断连、日亏损/最大回撤的独立 RiskPolicy 裁决、decision stale、仓位/API 上限、重大事件硬窗口和运行健康底线仍硬拦。
- NFP/GVZ/重大事件等事件风险在 live 中只能作为 `RiskPolicyService` 输入；`ExecutionGate` 的事件过滤保留给 backtest/legacy 兼容。
- live 因子决策不得使用当前未闭合 K 线；已闭合 bar 的 OHLC 是不可变因子输入，`spot_quote` 只能用于执行参考价、滑点判断和持仓保护，不得覆盖 bar 的 close/high/low，也不能把旧 bar 信号变成新信号。同一根已闭合 bar 不得重复 append 到 `StreamingFactorEngine`，也不得重复生成 open 决策；重复 loop tick 只能执行持仓观察、close/reduce/tighten 和保护修复。若 `decision_freshness.schema_version=decision_bar_freshness.v1` 且 `fresh=false`，开仓必须由 `RiskPolicyService` 返回 `decision_bar_stale`；若 bar fresh 但 `age_seconds` 超过 `max(180s, 1.5 * timeframe_seconds)`，开仓必须返回 `decision_signal_age_stale`。持仓监督的 close/reduce/tighten 仍可继续。
- live open-trade pipeline 只编排候选 sizing、`RiskPolicyService.evaluate("open_trade")`、market-session/order block、broker order 和 post-fill audit；它不拥有独立风控事实源。broker submit 线性化由 `backend.services.live_open_submission` 拥有：final admission/PG probe 在 admission lock 外，draining 在 RPC 前拒绝；RPC 一旦准入，fill resolution、entry protection、ledger/recovery 不受之后 stop 中断。新增开仓在 broker mutation 前必须通过唯一 producer 的 `open_learning_context.v2` 校验；缺少 entry cluster、market micro、完整 bar、execution、decision quality、event、data quality 或 market session 任一字段时 fail-closed，避免制造新的不可训练样本。confirmed open 后任一 post-fill 异常必须先落 no-new-risk latch，再尝试 fresh reconcile 并写 safety outbox；reconcile 自身异常不得跳出 fail-closed 路径。broker-confirmed open 的 SL/TP attach 状态机由 `backend.services.live_open_protection` 拥有：amend receipt 不能单独释放风险，只有 fresh position projection 精确确认 SL/TP 后才能 publish 并释放 matching pending cause；rejected/exception/projection mismatch 或后续 release/record 异常统一保持 unverified/fail-closed。filled/amended success/failure 的 attribution、learning context、ledger、recovery 与 decision-log 顺序由 `backend.services.live_open_processing` 拥有；成交后要求真实 fill price 并写入 `open_context_quality.ready=true`；amend failure 固定先 latch，ledger 辅助失败不得阻断 filled-open recovery 尝试。`live_service` 对三者只注入 runtime callbacks，新模块不直接调用 bridge market buy/sell/close API。同一 bar（`decision_ts`）只允许一次成功开仓：`_run_open_trade_pipeline` 在 candidate 前查 canonical risk_decision events 已存在该 bar 的 `open` 记录时以 `bar_already_opened` blocker 拒绝，覆盖 stale decision bar repair 重放与 pending open retry 重入两条路径；该去重是重复防护而非风险门，ledger 不可读时 fail-open 放行（只告警不阻塞），不同 bar 仍允许并发持仓。

- `position_supervisor:profit_protection.v1` 对 thesis-broken 判断采用最小证据窗与确认证据：未确认或证据窗未完成时固定 `hold/observe`，不得仅因瞬时 `broken` 在亏损侧 tighten；超过证据窗只代表 `thesis_break_ready`，还必须有接近原始入场止损、regime confirmed、time decay、连续 thesis broken 确认或信号反转等强证据，才允许 `thesis_broken` full close。已形成累计 MFE 后的真实 profit giveback 可独立优先 reduce；close/reduce/tighten 仍必须经过 `RiskPolicyService`。

- supervisor 的可交易部分平仓必须即时写入 `trade_executions.exec_type=reduce`，最终 close 仍只对整笔交易做一次因子归因；真实 PnL 以 `execution.deal_sync` 聚合同一 position 的全部 close legs 为准，不能只取最终 close deal。
- live session 风控统计固定使用 UTC 风控日，以 canonical broker_deal events 按最终平仓日、position 聚合重建；快照必须携带 `session_date_basis=utc_risk_day`、UTC window，并另带 `Asia/Shanghai` 自然日只读汇总供运营展示，后者不能驱动熔断。`session_start_balance` 由 broker 当前 balance 减去当日已实现净 PnL 重建；`runtime_kv[live.session_state.*]` 只作为进程恢复缓存，不能覆盖 broker close facts。
- 平仓后验必须以完整持仓路径区分入场与退出责任：`MFE/MAE`、profit capture、giveback 和 time-in-profit 决定 `good_win/lucky_win` 与责任归属，不能只按最终盈亏或因子贡献正负贴标签。最近三小时内连续两笔同方向 `bad_loss` 且带 factor-conflict/thesis/regime 失败证据时，live 复用现有 supervisor re-entry/RiskPolicy 硬闸门暂停该方向一小时；该闸门只消费已落库 review，不直接改因子权重。
- 同品种存在反向持仓时，开仓必须由 `RiskPolicyService` 以 `opposite_direction_position_open` 硬拦；系统不支持隐式 hedge/flip，未来如果要反手必须走显式“先平后开”动作链。
- 非 demo 的 context policy 或 Kelly sizing 把建议仓位压到 broker 最小交易量以下时，live 开仓候选必须以 0 volume 进入风控并被 `non_positive_requested_volume` 阻断，不能悄悄恢复为最小仓位；demo autonomous/nursery 的低样本、非正 Kelly 或正 Kelly 低于最小量的探索例外必须带 `demo_exploration` trace，`demo_nursery` 还保留 `demo_nursery_exploration` 兼容标记。
- 历史 tick 采集链已退役并删除；live 实时报价事实源仍是 cTrader `ProtoOASpotEvent`，不得因删除历史 tick 库而删除或绕过 spot quote、持仓保护与执行参考价链路。
- `risk/pre_trade.py`、`risk/circuit.py` 属于 paper/backtest 兼容风控，不是当前 live 主授权口；未接线的 legacy `execution/router.py` 已移除。
- 模型阶段裁决必须复用 `backend.services.model_permissions`，不能维护第二套模型权限事实。
- BB 不进入 ExecutionGate 作为硬过滤器。

判断原则：

- 模型输出默认 advisory/shadow。只有 PIT v2 工件通过显式门槛并持有近期 V16 delegate 后，才可在 `demo_nursery`/`demo_autonomous` 进入 `demo_canary`/`demo_active`；模型不能放宽规则、增加仓位、改变方向、修改硬风控或直接调用 broker。
- 后续自治治理推进必须能映射到当前 production plan 和 acceptance matrix；不能证明减少 authority、闭合风险或完成验收的改动不应自动推进。
- 智能体链路以 `AgentAuthorityRegistryService` 为权责合同事实源；新增 source agent 或控制面前，必须先声明 allowed writes、required gates、authority state 和 forbidden actions。
- agent 生成治理候选前必须把 `agent_generation_context` 写入 lineage；该上下文包含 authority verdict、scorecard、近期负反馈和 review rules，只用于审查/复盘，不授权执行。
- 新提案若声明 `agent_context_required=true` 或来自需要 review 的 governance bridge，必须在 evidence 或 lineage 中携带 `agent_generation_context`；直接写 `policy_suggestion` 的新路径应复用 `backend.services.policy_suggestion_context.attach_policy_suggestion_agent_context()` 生成同一上下文；candidate bridge 写入 `policy_suggestion` 时同时在 evidence 顶层和 lineage 写标准 `agent_generation_context`；readiness `proposal_generation_context_coverage` 只读审计该覆盖率，缺新上下文 degraded，历史旧提案只标 legacy。
- 对仍处于可执行/审查链路且缺 required context 的旧 `policy_suggestion`，`ProposalRegistryService.repair_missing_generation_context()` 只能补当前审查上下文并标记 `repair_current_context` / `repair_context_is_current_not_original`；它不改变 proposal 状态、不批准、不应用，也不伪装成原始生成时上下文。
- `policy_suggestion` 旧行缺 `source_agent` 时必须通过 `infer_policy_suggestion_source_agent()` 统一推断来源；已知 LightGBM shadow/advisory schema 归入 `lightgbm_shadow_models` 并固定 `advisory_only` gate，不能默认归到 `autonomous_learning`。
- 智能体质量以 `AgentScorecardService` 为只读观测口径；scorecard 可以影响 Proposal Registry 路由、证据要求和 candidate review 严格度，高分只能提高审查优先级，不能直接放大权限、改权重或下单。
- `AgentBriefingContextService` 是多智能体统一战况简报；包含 chain health、proposal flow、scorecard、最近交易反馈、scope-relevant `experience_memory` 和治理覆盖率，只能作为 review/prompt/context 输入，不是执行授权。
- `DecisionPolicy` 的 `experience_priors` 是学习后验接口，不是旁路；由 `ExperiencePriorService` 从终态有界效果构造，只有样本量和置信度达标的 prior 才可在 0.85~1.15 范围内小幅修正权重，最终仍受 role/lifecycle/diversity/redundancy、RiskPolicy 和 mutation boundary 约束。组合决策由 `backend.services.market_regime` 优先使用显式 regime，否则从既有 trend/volatility context 生成低基数事实标签并写入 canonical risk_decision events；治理侧\"当前市场状态\"统一读 `project_current_market_regime()`（experience_memory.regime_id 只读投影），与组合决策各自消费同一解析器、不重复计算；trade review 必须保存 entry decision 的 `regime_id/entry_regime`，历史只允许从 canonical risk_decision events 事实回填。
- `scripts/learning_worker.py` 不得导入 `backend.services.live_service` 获取研究任务；feature engineering 与休市 LightGBM 任务归 `backend.services.learning_research_jobs`，跨进程市场状态只读消费 runtime health projection，避免加载 live 执行巨石及其进程内状态。
- 交易 lesson 由 `ExperienceBuilder` 计算 rich context，并统一通过
  `upsert_trade_lesson_memory()` 写入唯一 `trade_lesson_memory.v1` projection，identity 为
  `trade_lesson:{review_id}`；`live_review` writer、projection 和 reader 已删除。lesson 可附带
  `agent_attribution` / `feedback_agents`，用于把盈亏经验反馈给参与过提案、shadow audit 或
  LLM advisory 的 agent；该反馈是记忆和评分证据，不是自动奖惩执行入口。learning backfill
  复用同一 upsert 和 review source anchor，不再另写 `learning_backfill.v1` experience；
  controlled-close 历史修复也复用同一 upsert；legacy source/timestamp 启动修复 writer
  以及所有历史兼容 projection 已删除。pattern stats/suggestion evidence 复用 canonical
  lesson ID。
- `model_ready=true` 还必须配合 `allowed_uses` 包含 `supervised_training`，才可进入强监督训练。
- `train_weight` 由 `quality_score`、`integrity`、`causal_level`、`label_status` 共同决定。
- 历史缺失字段只能标 degraded/partial/missing，不能补造实时上下文。
- 交易复盘必须区分 `signal_bar_ts`、`decision_evaluated_at`、`order_submitted_at`、`fill_ts` 和 `close_ts`；用信号 K 线时间替代实际入场时间会污染持仓学习。

- live 实时执行状态以 cTrader 为准。

- cTrader 开仓不得使用“同方向最大 position ID”或 `positions_before[0]` 猜测成交仓位。无法从 broker execution response、order/deal 差分和 position 差分得到唯一 position 时，结果必须是 `unknown`、`success=false`，保留 execution intent 等待恢复，禁止重发。
- live 决策 K 线以 cTrader bridge 内存中的已闭合 live trendbar 为准；`ProtoOASubscribeLiveTrendbarReq` 是 live 热路径的唯一在线 bar source，live tick 只读该 frame 并在 stale/断流时阻断 alpha，不能在串行安全热路径中执行 history RPC、读月库或写 bar。启动历史由 cTrader 在线优先预热，本地月库只作启动/离线兜底；canonical `data_sync` scheduler 每 30 分钟通过主 cTrader bridge 低频回补月库，作为唯一 durable monthly writer。legacy startup history pull 已删除。closed/有界 maintenance wait 必须共同抑制无效持久化回补，不能把未闭合 bar 当成 `complete=true` 的决策输入；不得抑制恢复实时行情所需的 spot/trendbar 重订阅。
- 外部研究数据不能替代 broker 实时行情和执行状态。
- 不新增生产路径写入 SQLite state。

## 8. 运行数据到学习治理的闭环

以下链路是当前生产事实，不应另建平行实现：

- `PortfolioCompositor.context_state` 汇总已存在的 COT、实际利率、美元相关性、ETF 持仓和央行购金因子；`ContextPolicyService` 仅用极端宏观证据提高入场阈值并缩小仓位，不生成方向。
- Web access token 刷新以“发起失败请求时使用的 token”为并发版本。旧 token 的迟到 `401` 若发现同源 token 已更新，只能复用新 token 重试，不能再次旋转 refresh session；同源多标签页使用 Web Locks 串行 refresh authority，并在锁内重验 token。跨标签页 token 变化通过 `storage` 事件同步，只有当前 token 的真实 refresh/retry 仍失败时才清理会话并跳转登录。
- `ProbabilityCalibrator` 校准组合信号置信度；校准结果通过 context policy 只允许缩仓，不允许放大原始仓位，缺失或损坏 artifact 时退化为 identity。
- `PositionQualityLightGBMService.score_position_context` 使用 trace-time PIT v2 特征；未晋级时只写 supervisor evidence，晋级后也只能把 rule `hold` 收紧为 tighten 或最多 25% reduce，并显式禁止 full-close fallback。Demo 当前仓位评分不拥有 broker 或风险参数写权限。
- `FactorGovernanceLightGBMService.materialize_demo_governance_advisories` 只有在对应 PIT v2 工件已晋级时，才为当前 `used_in_score=true` 的 alpha 生成 `downweight` suggestion；实际权重变化仍经过 Governor、DecisionPolicy、RiskPolicy、FactorWeightChangeService、overlay/snapshot 和 learning effect。目标失活时旧建议自动 supersede。
- open quality 晋级后位于 RiskPolicy 与成本边际检查之后，只能额外 veto；position quality 只能在仓位监督边界内收紧或有限减仓；factor governance 只能生成治理建议。模型不得计算最终仓位、修改硬风控或绕过 RiskPolicy。
- canonical trade_review events 会成熟 supervisor trajectory；成熟 open outcome 同步进入 `shadow_trades.factor='__portfolio_shadow__'`，用于组合级而非单因子级后验统计。
- 因子权重单次最大变化达到 `0.10` 时，`FactorWeightChangeService` 要求最近 replay 为 `completed`、无错误且 evidence grade 为 A/B；否则变更停在应用账本写入之前。
- 上述最终动作仍必须经过 `RiskPolicyService`、runtime mutation overlay/snapshot 和 learning application effect observation，不允许模型或经验直接绕过权力边界。

## 9. 冲突处理顺序

当信息冲突时，按下面顺序判断：

1. 当前运行中的服务和数据库审计事实。
2. 当前代码入口和测试契约。
3. `docs/system-source-of-truth.md`、`docs/README.md`、对应 contract。
4. `docs/legacy-debt-register.md` 中的迁移说明。
5. 历史 planning 文档和旧注释。

历史 planning 文档和旧注释只能提供背景，不能单独作为实现依据。

## 10. 当前自治与学习闭环约束

- `RuntimeConfig.autonomy_expansion_frozen` 是非 Demo/实盘权限面的 fail-closed 开关；在 `demo_nursery` / `demo_autonomous` 中配置值可以继续保留为 `true`，但 effective freeze 固定为 `false`，AWE、因子生命周期晋升、Canary 阶段上升和 supervisor template auto-apply 继续运行。非 Demo 的 learning-repair auto-unfreeze 只能提交 `AutonomyControlPlan`，不得通过 caller `risk_reduction`、action 名或未被 overlay 接受的假成功绕过 Coordinator + V16；mutation 未 committed 时 freeze 必须保持。Demo 激进治理仍不得绕过 RiskPolicy、DecisionPolicy、V16 单次委派、runtime snapshot、实验 admission、后验 effect reconcile 和自动回滚/隔离。
- learning-repair readiness 的 supervisor 候选证据只接受 learning worker 生成且与当前 approved suggestion 精确绑定的 `learning_shadow` recovered trace；live loop 不读取 approved suggestion，也不再生产 `canary_shadow`。观察缺失、lineage 不匹配或只存在历史 live shadow 时 readiness 与 auto-unfreeze 均 fail-closed；最终解冻仍要求 Coordinator committed mutation + V16 finalize。
- Supervisor 反事实按 5/15/30/60/120 分钟分别成熟，只有完整 M1 覆盖才算成熟；60 分钟是治理门槛，120 分钟是完全成熟。
- Supervisor thesis-break 使用模板中的完整 bar 窗口和独立证据族；高波动/弱趋势至少 1 根新 M5，其他至少 2 根。硬风险可绕过窗口。
- Demo nursery 的 `would_block` 探索使用 PostgreSQL 原子 reservation：每原因 5/日、全局 15/日、同 setup 1/日，broker 未成交时释放。
- Supervisor template 的 50 笔 60 分钟成熟样本、两个 session 和两个 regime 仍作为 evidence readiness 展示，并继续按候选 `template_id`、创建时间和 shadow trace 严格归因；跨休市窗口或缺 M1 的记录只作为 ineligible 诊断样本。该 evidence readiness 对非 Demo template auto-apply 仍是硬门；Demo nursery/autonomous 可在证据未满时应用已批准候选，但必须保留 `demo_aggressive_governance=true`、`canary_evidence_ready=false` 审计，并继续经过 RiskPolicy、V16、snapshot、effect monitor 和自动回滚。
- 新责任归因以 alpha/gate/context/sizing role 为边界；gate/context 不得生成 alpha downweight。

## 11. 前端与 Tauri 客户端边界

前端重构不改变以下生产 authority：

| 客户端职责 | 唯一事实或执行权 | 客户端允许做什么 |
|---|---|---|
| live state | backend canonical live state + broker fresh reconcile | 只读 /ws/state 完整快照；不得 HTTP fallback、轮询或合并旧快照 |
| account/positions/risk | cTrader、PostgreSQL runtime schema、RiskPolicyService | 展示 endpoint-level fact；不得补零、重算或把缓存作为授权输入 |
| readiness | BackendReadinessSnapshotService + runtime_kv 投影 | 展示 blocker 和 freshness；不得重新计算 readiness 或解锁 |
| governance/release/incident | typed mutation、Coordinator、V16CommandGate、RiskPolicyService | 收集意图、确认、提交并展示 durable/audit/commit 结果；不得本地 apply |
| market/research | bars、external PIT、replay、learning 和治理只读投影 | 查询、筛选、引用和本地只读缓存 |
| credentials/session | auth_session、revocation ledger、一次性 WS ticket | access 仅内存；refresh/session 材料由 Windows Credential Manager 保护 |
| desktop shell | Tauri 2 / Windows WebView2 | 窗口、更新、诊断和最小 OS 能力；不运行交易或生产 writer |

Tauri 2 只是桌面交付壳，React 19 renderer 只是事实消费和动作编排界面。
它们不形成第二个服务端、第二个 live state writer、第二个 risk calculator 或
第二个 governance store。

本地 IndexedDB 只允许保存行情、回放、因子证据和研究/学习/治理只读材料；
账户、持仓、风险、Safety、Readiness、control、认证结果、mutation 结果和
任何 access/refresh token 均不得进入缓存。离线只允许查看带 cache/stale 标记
的研究内容，重新在线后必须以服务端事实重新认证、重连和复核。

前端目标路由、旧路径删除、工作区交互、视觉 token、桌面安装/更新和验收门见
planning/frontend-refactor-plan.md、frontend-operator-contract.md、
frontend-desktop-contract.md 和 frontend-refactor-acceptance-matrix.md。
这些文档是消费规则，不改变本节列出的 authority；接口 contract 只有在真实
API schema 或状态机发生变化时才更新 api-fact-contract.md。
